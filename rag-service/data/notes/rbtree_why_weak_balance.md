# 红黑树为什么放松平衡仍能保证 O(log n)

## AVL 的严格平衡 vs 红黑树的弱平衡

AVL 树要求每个节点的左右子树高度差 ≤ 1（平衡因子 ∈ {-1,0,1}）。这保证了树高 ≤ 1.44 log₂(n)，查找极快，但插入/删除时可能需要多次旋转来修复。

红黑树只要求：
1. 每个节点非红即黑
2. 根是黑色
3. 叶子（NIL）是黑色
4. 红色节点的孩子必须是黑色（不能有连续红）
5. 从任一节点到其所有叶子后代的路径上，黑色节点数相同（黑高相同）

这些性质保证：最长路径 ≤ 2 × 最短路径。

## 为什么最长路径 ≤ 2×最短路径

- 最短路径：全黑节点，长度 = 黑高 bh
- 最长路径：红黑交替（不能连续红），长度 ≤ 2 × bh

所以树高 h ≤ 2bh。又因为黑高 bh ≥ h/2，而 n ≥ 2^bh - 1（满二叉树的最少节点数），所以：

n ≥ 2^(h/2) - 1 → h ≤ 2 log₂(n+1)

即树高是 O(log n)，只是常数比 AVL 大（AVL 是 1.44，红黑树是 2）。

## 为什么"放松"反而更好

| 维度 | AVL | 红黑树 |
|------|-----|--------|
| 查找 | 更快（树更矮，1.44 log n） | 稍慢（2 log n） |
| 插入旋转 | 最多 2 次（但可能回溯到根） | 最多 2 次 + 着色 |
| 删除旋转 | 可能 O(log n) 次（逐层回溯） | 最多 3 次 |
| 适用场景 | 读多写少（数据库索引、字典） | 写多读少（STL map/set、Linux CFS、epoll） |

红黑树的优势在于：插入/删除的修复代价有常数上界（最多 2-3 次旋转），而 AVL 删除时可能需要从叶子一路旋转回根（O(log n) 次）。在频繁插入删除的场景（如操作系统调度器、STL 容器），红黑树的写性能更稳定。

## 旋转时 parent 指针怎么更新

旋转（以左旋为例，x 左旋）：
```
    p              p
    |              |
    x              y
   / \    →      / \
  a   y         x   c
     / \       / \
    b   c     a   b
```

指针更新顺序：
1. x.right = y.left（b 挂到 x 右边）
2. if y.left: y.left.parent = x
3. y.parent = x.parent（y 继承 x 的父）
4. if x.parent == nil: root = y; elif x == x.parent.left: x.parent.left = y; else: x.parent.right = y
5. y.left = x
6. x.parent = y

关键：先处理孩子关系，再处理父子关系，最后把 x 挂到 y 下面。顺序错了会出现悬空指针或环。

## 面试高频问题

- 为什么红黑树不需要像 AVL 那样记录平衡因子：五条性质通过颜色隐式约束了路径长度比，不需要额外数值
- 红黑树插入后最多几次旋转：2 次（叔叔红→着色上移可能多次，但旋转最多 2 次）
- 为什么 Java TreeMap/HashMap 用红黑树不用 AVL：HashMap 的树化桶可能频繁增删，红黑树写代价更稳定
- 把红节点染成黑色会违反什么：可能违反性质 5（黑高不一致），某些路径多了一个黑节点
- Linux CFS 调度器为什么用红黑树：进程频繁插入/删除（创建/退出），需要 O(log n) 且写代价有常数上界
