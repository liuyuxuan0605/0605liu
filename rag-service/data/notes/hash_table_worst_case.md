# 哈希表最坏情况退化与优化

## 平均 O(1) 的前提

哈希表的 O(1) 查找/插入/删除是均摊复杂度，前提是：
- 哈希函数分布均匀（每个桶被命中的概率接近 1/capacity）
- 负载因子（load factor = 元素数 / 桶数）控制在合理范围（通常 < 0.75）
- 冲突解决策略高效

## 最坏情况 O(n) 的退化条件

当所有键都映射到同一个桶时，哈希表退化为链表（或数组线性扫描），查找/插入/删除全部变成 O(n)。触发条件：

1. 哈希函数极差：如 hash(x) = 0（所有键进同一个桶）
2. 恶意构造：攻击者知道哈希算法后故意构造大量同桶键（HashDoS 攻击）
3. 负载因子过高：桶数不够，即使哈希均匀也会有大量冲突
4. 键的分布特殊：如所有键都是 capacity 的倍数，取模后全落到桶 0

## 冲突解决策略对比

### 链地址法（Separate Chaining）
- 每个桶挂一个链表，冲突元素追加到链表尾部
- 最坏 O(n)：所有元素在一条链上
- 优点：实现简单、删除方便、负载因子可以 > 1
- 缺点：指针开销、缓存不友好

### 开放寻址法（Open Addressing）
- 冲突时按探测序列（线性探测/二次探测/双重哈希）找下一个空桶
- 最坏 O(n)：表几乎满时探测序列遍历整个表
- 优点：缓存友好（数据连续存储）、无指针开销
- 缺点：删除需要"墓碑"标记、负载因子不能太高（通常 < 0.7）

## Java 8 HashMap 的红黑树优化

Java 8 对链地址法做了关键改进：当某个桶的链表长度超过阈值时，将链表转换为红黑树。

- 树化阈值（TREEIFY_THRESHOLD）：链表长度 ≥ 8 且数组长度 ≥ 64 时转红黑树
- 退化阈值（UNTREEIFY_THRESHOLD）：红黑树节点数 ≤ 6 时退回链表
- 数组最小树化容量（MIN_TREEIFY_CAPACITY）：64（数组太小时优先扩容而非树化）

效果：最坏情况从 O(n) 改善为 O(log n)。即使所有键落在同一个桶，查找也只需遍历一棵平衡树。

为什么阈值是 8：在理想哈希分布下，桶内元素数服从泊松分布，长度达到 8 的概率约为千万分之六。正常情况下几乎不会触发树化，只有极端冲突（恶意攻击或极差哈希）才会用到。

## 如何避免退化

1. 选择好的哈希函数：分散均匀、雪崩效应（输入微小变化导致输出巨大变化）
2. 控制负载因子：超过阈值（如 0.75）时扩容（capacity 翻倍 + 全量 rehash）
3. 随机化哈希种子：防止 HashDoS 攻击（如 Java String 的 hashSeed 随机化）
4. 树化兜底：Java 8 的红黑树方案，即使最坏也不超过 O(log n)
5. 双重哈希：开放寻址中用第二个哈希函数决定探测步长，减少聚集

## 面试要点

- "哈希表 O(1)"是均摊/期望复杂度，不是最坏保证
- 最坏 O(n) 的根因是所有键聚集在同一个桶
- Java 8 红黑树优化把最坏从 O(n) 降到 O(log n)，代价是树节点的内存开销（约为链表节点的 2 倍）
- 扩容（rehash）是 O(n) 操作，但均摊到每次插入仍是 O(1)
- 线程安全：HashMap 非线程安全，并发用 ConcurrentHashMap（分段锁 / CAS + synchronized）
