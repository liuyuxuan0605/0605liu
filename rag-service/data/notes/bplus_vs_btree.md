# B+ 树与 B 树的区别

## B 树（B-Tree）回顾

B 树是一种自平衡的多路搜索树，每个节点最多有 m 个孩子（m 阶）。所有节点（包括内部节点和叶子）都存储 key 和 data。查找时在任何一层命中即返回。

特性：
- 所有叶子在同一层（绝对平衡）
- 内部节点存 key + data + 子指针
- 节点内 key 有序，支持二分查找
- 插入/删除可能触发分裂（split）或合并（merge）

## B+ 树的结构

B+ 树是 B 树的变体，专为磁盘 I/O 优化（数据库索引、文件系统）：

- 所有 data 只存在叶子节点；内部节点只存 key 和子指针（纯索引）
- 叶子节点之间用双向链表串联（支持范围扫描）
- 查找必须走到叶子层才能拿到数据（不存在"中间层命中"）

## B+ 树 vs B 树

| 维度 | B 树 | B+ 树 |
|------|------|-------|
| 数据存储位置 | 所有节点 | 仅叶子节点 |
| 内部节点内容 | key + data + 子指针 | 仅 key + 子指针 |
| 单次查询稳定性 | 不稳定（可能第 1 层命中，也可能第 3 层） | 稳定（必须走到叶子，路径长度固定） |
| 范围查询 | 需要中序遍历（跨层，随机 I/O） | 叶子链表顺序扫描（连续 I/O，极快） |
| 扇出（fan-out） | 较小（内部节点存 data 占空间） | 较大（内部节点不存 data，同页能放更多 key） |
| 树高 | 较高 | 更矮（扇出大 → 同样数据量层数更少） |
| 磁盘 I/O 次数 | 较多 | 更少（树矮 + 内部节点小） |

## 为什么 B+ 树更适合数据库索引

1. 内部节点不存 data → 同样大小的磁盘页（通常 4KB/16KB）能容纳更多 key → 扇出更大 → 树更矮 → 查询时磁盘 I/O 次数更少。典型：3-4 层 B+ 树可索引数亿行数据。

2. 叶子链表 → 范围查询（WHERE age BETWEEN 20 AND 30）只需定位到起始叶子，然后沿链表顺序读，无需回溯父节点。B 树的范围查询要做中序遍历，跨层随机 I/O。

3. 查询路径长度固定 → 任何 key 的查找都是 O(树高)，性能可预测。B 树可能在第 1 层就命中（快），也可能到叶子才命中（慢），方差不齐。

## 为什么叶子节点要链表串联

没有链表时，范围查询 [l, r] 需要：找到 l → 回溯到公共祖先 → 再向下找下一个 key → 反复回溯。每次回溯都是一次磁盘随机读。

有链表时：找到 l 后，沿 next 指针顺序读直到 > r。全部是顺序 I/O，对磁盘/SSD 都极友好。

## 分裂（Split）操作

B+ 树插入时节点满了（key 数 ≥ m）：
- 叶子分裂：把 key 均分两半，右半新建节点，中间 key 复制到父节点（注意：是复制，不是上移——因为 data 必须在叶子）
- 内部节点分裂：把 key 均分，中间 key 上移到父节点（与 B 树相同）

## 面试高频问题

- B+ 树为什么比 B 树矮：内部节点不存 data，同页放更多 key，扇出从几十变成几百上千
- MySQL InnoDB 为什么用 B+ 树不用 B 树/红黑树/哈希：B+ 树矮（3 层索引亿级数据）、范围查询快（叶子链表）、磁盘友好；红黑树是二叉的太高；哈希不支持范围
- B+ 树的阶数怎么选：通常由磁盘页大小决定（16KB 页 / (key大小+指针大小) ≈ 阶数）
- 聚簇索引 vs 二级索引：聚簇索引叶子存完整行数据，二级索引叶子存主键值（回表查询）
